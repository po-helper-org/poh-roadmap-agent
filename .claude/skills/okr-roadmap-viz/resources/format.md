# Формат roadmap: `roadmap.md` + `backlog/`

Папка roadmap — одна цель (OKR-объектив) со всеми её треками:

```
.okr/roadmap/<slug>/
  roadmap.md        паспорт: роли, выходные, целевые состояния, треки, этапы своего трека
  backlog/          задачи своего трека — по файлу на задачу
    task-1 - Интервью с организаторами.md
  conditions/       реестр условий целевых состояний — по файлу на условие (необязательно)
    c-1 - Подписан договор с провайдером.md
  questions.csv     реестр вопросов и ключевых решений (необязательно)
  journal.csv       журнал комментариев и прогресса задач и вопросов (необязательно; строки только дописываются)
  roadmap.json      граф зависимостей и номера — пишет `roadmap.py lint`, руками не править
  roadmap.html      страница — пишет `roadmap.py build`, руками не править
```

Пишет и правит агент только `roadmap.md`, `backlog/*.md`, `questions.csv` и `journal.csv` (дописывает). Всё вычисляемое — номера
3.7.1, недели, граф, порядок, страница — делает скрипт. Эталон формата —
`scripts/fixtures/sample/`; эталон карты целевых состояний — `examples/school-migration/` (см. `constitution.md`).

Несколько стримов одной цели на одной странице — сборная карта: своя папка у каждого стрима и папка
цели, которая на них ссылается (раздел «Сборная карта цели из нескольких папок»).

`bin/roadmap init <папка> [--title …] [--track …]` — заготовка по конституции: паспорт со своим треком без
«- нумерация:», `backlog/ts1` (ЦС-веха: `role: PO`, `ordinal: 1`, `title` «1. …», `short` «1 · …», дата-заготовка),
`questions.csv` с колонками статьи V.1 и пустой `journal.csv` (UTF-8 с BOM, `;`, CRLF). `-h`/`--help` — справка;
неизвестный параметр, начинающийся с `-`, — ошибка (папку с таким именем init не создаёт).

## Модель

- **Цель** — вся папка. Заголовок страницы — `title` из `roadmap.md`.
- **Трек** — строка обзора. У чужих треков — результат, план по ролям и целевые
  состояния. **Свой трек** (в папке ровно один, `- свой: да`) раскладывается на этапы и задачи.
  На сборной карте цели своих треков несколько — по одному на папку стрима.
- **Этап** — группа задач своего трека (3.3, 3.4 …).
- **Задача** — файл в `backlog/`. Бывает задачей с периодом, вехой (одна дата) или
  блокером (дата, когда снимется). Задачи вкладываются через `parent`.
- **Целевое состояние** — веха roadmap: у трека (одна неделя) или у всей цели
  (может длиться несколько недель).

start: 2026-09-28          # необязательно: первая неделя шкалы; по умолчанию — неделя самой ранней даты

Роли по умолчанию, если раздела нет: PO, SA, BE, FE, DEVOPS, DELIVERY.
Даты везде — `ГГГГ-ММ-ДД`.

## `backlog/<id> - <название>.md`

Файл задачи — frontmatter и текст, как у [Backlog.md](https://github.com/MrLesk/Backlog.md).
Имя файла роли не играет, связь — по `id`.

```markdown
---
id: task-6
title: API продажи абонемента
status: Открыт            # Открыт | В работе | Ревью | Заблокировано | Выполнено (To Do / In Progress / Done тоже)
role: BE                  # ключ из «## Роли»
type: task                # task | milestone | blocker
stage: dev                # id этапа; у подзадачи не нужен — этап наследуется от родителя
parent: task-5            # необязательно: задача-родитель
feature: 1.1              # необязательно: код из «### Фичи»; у подзадачи наследуется от родителя
ordinal: 20               # порядок среди соседей; без него — по id
start: 2026-12-07         # у задачи — период start..end
estimate: не подтверждена  # необязательно: «подтверждена» — срок оценила техническая команда (со слов команды или PO);
                          # «не подтверждена» — полоса со штриховкой и пометкой, у задач без дат — пунктирный контур
                          # в окне родителя «только scope»; на странице наследуется потомками. В пакете руководству .xlsx
                          # даты стоят только у задач со своим «подтверждена» или со статусом «Выполнено» (раздел ниже)
end: 2027-01-22
date: 2026-12-04          # у вехи и блокера — одна дата (или end)
progress: 40              # 0…100
dependencies: [task-4, stage:analytics]   # «стартует после»: задачи и целые этапы
customer: Бизнес-владелец  # заказчик
assignee: Команда Core    # исполнитель
approver: CTO платформы Б   # согласующий
short: Витрина            # краткое название на шкале
---

Описание: что делаем, критерий готовности, ссылки. Попадает во вкладку «Описание».

## Комментарии

- 2026-11-02: черновик отправлен бизнесу     заметки о состоянии, по дате (прежний способ)
```

Раздел «## Комментарии» читается как раньше (на странице — с пометкой «md»), но новые комментарии и прогресс
пиши в журнал папки `journal.csv` (раздел «Журнал комментариев и прогресса»): туда же их дописывает архив страницы.

Обязательны `id`, `title`, `role`. Остальное — по мере знания: задача без дат
видна в дереве, но не на шкале.

В `title` можно сослаться на другую задачу: `Решение по итогам {#task-12}` — на
странице подставится её номер.

### Фичи

Этап отвечает на «когда и в каком порядке» (процессная карта), фича — на «что умеет
система» (релизная карта). `feature` ставь только работам, которые делают систему
(разработка, её подзадачи и вехи-результаты); аналитике, согласованиям, решениям,
блокерам и вопросам — нет: это процесс, их место на карте этапов. На карте этапов у
работы с фичей — метка кода фичи (`1.1.2.1`), так релиз читается внутри процесса; в режиме
«Фичи» блокеры и вопросы не показываются, работы без фичи сведены в одну строку-сноску. Одна
задача стоит в одном этапе и в одной фиче. На странице своего трека переключатель
«Этапы / Роли / Фичи»: в режиме «Фичи» строка фичи — сводная полоса по всем её
задачам и подфичам, ромбы контрольных точек (вехи и блокеры с датой) с подписью даты,
«до ДД.ММ» — финиш. Фича без задач — «не спланировано». Задачи без `feature` — в группе
«Вне декомпозиции фич».

### Нумерация

Считает скрипт, в файлах номеров нет: `<нумерация>.<k>` — сначала задачи своего трека
без этапа, затем этапы в порядке «### Этапы», внутри — по `ordinal`, вложенные —
`2.3.1.2`. Не нумеруются блокеры и задачи, чьё название начинается с `БЛОКАТОР`,
`ВОПРОС`, `ЖДЕМ`, `ВЛИЯЕТ`, `РИСК`.

## Сборная карта цели из нескольких папок

Цель, у которой несколько стримов, и каждый стрим ведётся в своей папке со своим реестром вопросов. Сборная
карта — отдельная папка с одним `roadmap.md`: паспорт цели и треки, каждый из которых ссылается на папку стрима.
На странице все такие треки — свои: на обзоре строка на трек, клик открывает дерево трека (ЦС → шаги → подзадачи,
этапы, роли, фичи) так же, как у своего трека одиночной папки.

```
.okr/roadmap/
  goal-01/roadmap.md            паспорт цели: title, роли, выходные, целевые состояния цели, треки с «- папка:»
  courses/                      стрим — обычная папка roadmap: roadmap.md (свой трек), backlog/, questions.csv
  corporate/                    ещё один стрим
```

```markdown
---
title: Цель 01. Переезд онлайн-школы на платформу Б — целевые состояния
start: 2026-11-02
---

## Роли
- PO | Product Owner | #c98a00

## Выходные недели
- 2026-12-28

## Трек 1. Курсы и ученики
- папка: ../courses          путь к папке стрима относительно папки цели

## Трек 2. Корпоративные клиенты
- папка: ../corporate
- нумерация: 2                       необязательно: иначе — нумерация своего трека стрима

### Результат                         необязательно: иначе — из своего трека стрима
```

- **Загрузка.** `lint` и `build` сборной папки загружают каждую папку стрима тем же парсером и с теми же
  проверками, что и одиночную. Ошибки и предупреждения стрима выводятся с путём его папки; ошибка в любом стриме —
  сборки нет. Файлы стримов сборка не меняет: одиночная страница стрима собирается как раньше.
- **Что откуда.** Номер и название трека — из заголовка `## Трек N. Название` паспорта цели. Нумерация, результат,
  план по ролям и целевые состояния трека — из паспорта цели, если там заданы, иначе — из своего трека стрима. Этапы,
  фичи, задачи, условия, реестр вопросов — только из папки стрима. Роли — из паспорта цели; роль, которой там нет, —
  из папки стрима. Выходные — паспорта цели и всех стримов. Чужие (обзорные) треки стрима на сборной странице не
  показываются: там этот стрим — свой трек.
- **Пространство имён.** Внутри сборки id задачи — `<N>:<id в файле>` (`ts4` трека 2 → `2:ts4`), этапа и условия —
  так же: одинаковые id в разных стримах не конфликтуют. `dependencies`, `parent`, `{#id}`, «Влияет на» и `depends`
  пишутся в файлах как обычно — id своей папки; связей между стримами нет. В `roadmap.json` сборной папки у задачи —
  `track` и `rid` (id в файле). На странице правки и «Скопировать промпт» указывают полный путь к файлу стрима
  и id из файла. Одинаковые названия этапов в разных треках различаются пометкой « · трек N».
- **Реестр вопросов — объединённый.** Вопрос с одним ID в нескольких реестрах показывается один раз: «Влияет на» и
  «История» объединяются, остальные поля — из реестра, в «Комментарии» которого нет пометки «Общий вопрос…» (в копиях
  она есть). Предупреждение `lint` — если «Вопрос», «Ответ», «Ответственные», «Критичный» или «Статус» в копии
  расходятся с основным реестром, и если пометка стоит не во всех копиях, кроме одной. На странице «Реестр вопросов»
  вкладки сгруппированы по трекам («1 · ЦЕЛЬ 3», «2 · ЦЕЛЬ 1»); вопрос стоит во вкладке первой задачи из «Влияет на»,
  во вкладках других затронутых целей — строка-ссылка «Влияют и на эту цель». В карточке вопроса — его реестр и копии.
- **Нельзя:** `backlog/` и `conditions/` в папке цели (только в стримах); `- свой: да` без `- папка:`; этапы и фичи в
  паспорте цели; папка стрима, которая сама сборная карта; одна папка дважды. Условие стрима, привязанное к
  целевому состоянию его чужого трека или всей цели стрима, на сборной странице не показывается (предупреждение).
- `tree` печатает треки по очереди; `questions <папка> <id>` принимает id из файла (`ts4`), если он есть только в одном
  стриме, иначе — `<N>:<id>`. `bin/check-qlinks <папка цели>` проверяет каждую папку стрима по её реестру.
- Архив «Экспортировать» сборной страницы кладёт папку цели и стримы рядом (`map/goal-01/`, `map/courses/` …),
  восстановление — `roadmap.py build map/goal-01`.
- **Журнал** — `journal.csv` в папке каждого стрима (в папке цели не читается — предупреждение). Объект пишется id из
  файла своей папки (`s11`, а не `1:s11`) или ID вопроса её реестра; на странице запись о задаче — в пространстве
  имён трека (`1:s11`), о вопросе — у объединённого вопроса (записи всех реестров вместе). Запись со страницы уходит
  в журнал папки задачи, а о вопросе — в журнал папки его основного реестра (без пометки «Общий вопрос…»); в архиве —
  `map/courses/journal.csv`, `map/corporate/journal.csv`.

## Проверки `lint`

Ошибка — сборки не будет:

- нет `id`, `title`, `role`; повтор `id`; роль, этап или родитель, которых нет;
- дата не `ГГГГ-ММ-ДД`, `end` раньше `start`, `progress` вне 0…100;
- зависимость на несуществующую задачу или этап, на себя, на свой этап, на предка
  или потомка; цикл зависимостей (в том числе через этап); цикл `parent`;
- `{#id}` в названии на несуществующую задачу;
- задачи есть, а своего трека нет, или своих треков больше одного (в папке; сборная карта — раздел выше); этапы или фичи у чужого трека;
- `feature`, которой нет в «### Фичи»; код фичи дважды;
- `journal.csv`: нет колонки, дата, тип, прогресс или статус не по формату, объект не из этой папки (раздел «Журнал …»).

Предупреждение — сборка будет:

- задача стартует не позже финиша того, после чего должна идти (на странице — подсветка);
- подзадачи выходят за `start..end` родителя — родитель не короче подзадач: растяни его до самой ранней и самой поздней даты потомков;
- веха без даты; `progress: 100` без статуса «Выполнено»; одинаковый `ordinal` у соседей;
- этап без задач; поле или раздел, которые сборка не читает;
- `progress` или `status` во frontmatter расходятся с последней записью «прогресс» журнала;
- срок ответа открытого вопроса позже старта задачи из его «Влияет на» (раздел «Реестр вопросов»);
- `lint <папка> --date ГГГГ-ММ-ДД` — ещё и открытый вопрос, чей срок ответа раньше этой даты. Без `--date` эта проверка
  не делается: `lint` не зависит от дня запуска (одинаковые файлы — одинаковый вывод и `roadmap.json`).

## Реестр вопросов и решений: `questions.csv`

Полный список вопросов и ключевых решений — одна таблица рядом с `roadmap.md`. Она
самодостаточна: её можно открыть в Excel и переслать без Roadmap. В Roadmap вопросы
попадают через `lint` — по колонке «Влияет на».

```
ID;Этап;Вопрос;Ответ;Ответственные;Влияет на;Комментарий
Q-01;1.R · решения;Кто и с кем заключает договор?;;Бизнес-владелец;"r3 — Договор
s15 — Публикация";Источник: PO
```

- UTF-8 (можно с BOM), разделитель `;` или `,`; ячейку с переносами строк — в кавычках.
- «Влияет на»: по строке на задачу, **первое слово строки — id задачи** из `backlog/`, дальше —
  название для читателя таблицы. Вопрос подзадачи виден и у её родителя.
- «Ответ» пуст — вопрос открыт. Источник вопроса (кто задал) — в «Комментарии».
- Необязательная колонка «Критичный»: «да» — вопрос критичный. На странице у задачи — «всего / критичных открытых / отвечено»
- Необязательные колонки «Статус» и «История». Статус вопроса: Создан | Назначен | В работе | Ревью | Готово. Пусто — выводится
  сам: есть ответ — «Готово», есть ответственный — «Назначен», иначе «Создан». «История» — по строке на запись:
  `ДД.ММ.ГГГГ | Статус | заметка` (дата информационная, пустая допустима). Сюда записывают смещения и статусы с каждого созвона;
  на странице они видны в сайдбаре вопроса (клик по строке реестра).
  (серым, красным, зелёным).

`lint`: ошибка — нет колонки, нет ID или текста вопроса, ID повторяется, «Влияет на» ссылается на
несуществующую задачу; предупреждение — вопрос ни на что не влияет, открытый вопрос без ответственных, срок ответа
открытого вопроса позже старта задачи из «Влияет на» (задача стартует без ответа — срок раньше или сдвиг старта решает
PO), с `--date` — срок ответа открытого вопроса прошёл. **Срок ответа** — последнее «до ДД.ММ.ГГГГ» в «Комментарии» и
«Истории» (`xlsx_pack.due`, как на листе «Реестр вопросов» и в дейлике); пиши его формулой «Срок ответа: до ДД.ММ.ГГГГ».
На странице: вкладка «Реестр» в карточке задачи и страница «Реестр вопросов» (кнопка рядом с «Roadmap»).
`questions <папка> [<id задачи>] [--open]` — реестр текстом для агента: по этапам, у задачи — с подзадачами.

## Журнал комментариев и прогресса: `journal.csv`

Один файл на папку рядом с `questions.csv`: комментарии и прогресс задач и вопросов этой папки, по строке на запись.
Формат как у `questions.csv`: разделитель `;`, UTF-8 с BOM, переводы строк CRLF, ячейку с `;`, кавычками или переносом —
в кавычках. **Строки только дописываются в конец**: журнал — история, старые строки не правят и не удаляют (ошибся —
допиши исправление). Нет записей — файл с одним заголовком (так заведён `corporate/` в примере; `init`
создаёт такой же).

```
Дата;Объект;Тип;Прогресс;Статус;Текст;Автор
2026-11-02;task-2;прогресс;40;В работе;Черновик требований собран;SA
2026-11-09T10:30;task-2;комментарий;;;Возвраты согласуем на созвоне;PO
2026-11-19T14:05;Q-07;комментарий;;Назначен;Провайдера уточнить у бизнеса;
```

| Колонка | Что | Обязательна |
|---|---|---|
| Дата | `ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДДTчч:мм` (страница пишет с временем, местное время) | да |
| Объект | id задачи из `backlog/` этой папки или ID вопроса из её `questions.csv` | да |
| Тип | `комментарий` или `прогресс` | да |
| Прогресс | целое 0…100 — у «прогресс» обязательно, у «комментарий» пусто | колонка — нет |
| Статус | статус на момент записи: у задачи — Открыт · В работе · Ревью · Заблокировано · Выполнено, у вопроса — Создан · Назначен · В работе · Ревью · Готово | нет |
| Текст | у «комментарий» обязателен, у «прогресс» — пояснение | да |
| Автор | кто сказал; пусто — PO | колонка — нет |

- **Порядок** — детерминированный: по Дате (строкой: `2026-11-09` раньше `2026-11-09T10:30`), при равной — по
  строкам файла. Одинаковые файлы — побайтно одинаковая страница; метка сборки — sha данных, журнал в них входит.
- **Прогресс задачи** на странице и в `roadmap.json` — последняя (в этом порядке) запись «прогресс»; её Статус, если
  заполнен, — статус задачи на странице. Журнал важнее frontmatter: `progress`/`status` в md, которые с ним
  расходятся, — предупреждение `lint` (обнови поле тем же значением или убери `progress`). Записей «прогресс» нет —
  как раньше, из frontmatter.
- **Прогресс без своего значения — расчёт по подзадачам.** У задачи без своего прогресса (нет записей «прогресс» в
  журнале и `progress` в md) и не «Выполнено» — обычно шаг и ЦС — страница и лист «ГАНТТ» пакета .xlsx показывают
  среднее по подзадачам, которые входят в прогресс: то же правило, что в дейлике (раздел «Дейлик», «Прогресс задачи на
  дату»; код — `roadmap.Progress`, один на страницу, .xlsx и дейлик). На странице значение — курсивом с подчёркиванием
  точками, в подсказке и карточке задачи: «расчёт по подзадачам: N — своего прогресса нет, среднее на момент сборки»;
  в .xlsx — курсивом, с примечанием ячейки. Считается при сборке: прогресс подзадачи, изменённый на странице, попадёт в
  расчёт родителя после переноса в журнал и пересборки. В md ничего не пишется; PO назвал прогресс шага — запись
  «прогресс» журнала, она важнее расчёта.
- **На странице**: в карточке задачи вкладка «Комментарии» — записи журнала (комментарии и прогресс), комментарии из
  «## Комментарии» md и несохранённые записи страницы, у каждой — источник (`journal.csv`, `md`, `не сохранено`);
  в карточке вопроса — записи о нём во вкладке «История» и комментарии во вкладке «Комментарии».
- **Прогресс у вопроса** не бывает (ошибка); у вопроса — «комментарий», можно со Статусом.
- `lint`: ошибка с номером строки — нет колонки «Дата», «Объект», «Тип» или «Текст»; дата не по формату или
  несуществующая; объект не из этой папки; неизвестный тип; прогресс вне 0…100, у «комментарий» или у вопроса; статус
  не из словаря объекта; комментарий без текста. В `roadmap.json` — `journal` (записи по порядку, с файлом и строкой).

### Путь записи со страницы

1. PO оставляет комментарий к задаче или вопросу, меняет прогресс или статус задачи — запись (Дата с временем, Объект,
   Тип, Прогресс, Статус, Текст, Автор PO) попадает в **несохранённый журнал** браузера (`localStorage`, ключ
   `rm-journal-v1-<slug>`, без метки сборки — переживает пересборку). Несколько правок прогресса одной задачи за день —
   одна запись; вернул прогресс и статус как в сборке — записи нет. Несохранённую запись можно удалить, сохранённую — нет.
2. «Экспортировать» кладёт в архив `journal.csv` каждой затронутой папки = исходный файл как есть + несохранённые
   записи в конец (по Дате, затем по времени добавления); файла не было — с заголовком. `roadmap.py build
   <архив>/map` (сборная — `map/<папка цели>`) сразу показывает их.
3. Страница из новой сборки узнаёт свои записи по ключу «Дата + Объект (id в файле) + Тип + Прогресс + Текст» и
   убирает их из несохранённого журнала — повторов нет. Чего в журнале сборки нет, остаётся несохранённым.
4. «Скопировать промпт» и `PENDING.md` перечисляют несохранённые записи готовыми строками для `journal.csv`
   с путём к файлу: агент дописывает их в конец (строки, которые уже есть, не повторяет).

## Реестр условий: `conditions/<id> - <название>.md`

Условие — то, на чём держится срок: без него веха или целевое состояние не наступит.
Привязано к одной цели: к вехе своего трека (`milestone: <id вехи>`), к целевому состоянию
трека (`track: 2`, `target:` — его дата) или цели целиком (`track: goal`, `target:` — первая
дата диапазона). На странице условия вехи — во вкладке «Реестр» её карточки (одно условие —
одна строка: состояние, условие, ответственный, срок, зависимости; клик раскрывает разделы),
все вместе — на странице «Реестр условий».

```markdown
---
id: c-1
title: Подписан договор с платёжным провайдером на рассрочку
milestone: task-5           # id вехи — или вместо него:
# track: 2                  #   номер трека или goal
# target: 2027-02-26        #   дата целевого состояния из roadmap.md
status: Открыт              # как у задач; «Выполнено» — условие наступило
owner: Бизнес-владелец      # ответственный — обязателен по смыслу (иначе предупреждение)
approver: CTO платформы Б   # кто принимает
due: 2026-12-18             # крайний срок: позже — целевое состояние сдвигается
depends: [task-10, task-6]  # задачи, которые должны закончиться к due (детерминированная часть)
risk: R1                    # необязательно: метка риска
short: Договор              # необязательно
---

Контекст: что неизвестно, кто участвует.

## Что должно произойти
## Если сдвигается          последствия: что и на сколько сдвинется
## Чтобы вернуться к плану   действия, кто, к какой дате
## Вопросы                  что ещё надо проработать
```

Состояние считается, не пишется (одинаково на странице и в `report`, на дату просмотра):

- **Выполнено** — `status: Выполнено`;
- **Сорвано** — `due` прошёл, а условие не выполнено;
- **В зоне риска** — условие заблокировано или у любой невыполненной задачи из `depends`:
  срок прошёл, срок позже `due`, задача заблокирована, у задачи нет срока. Вопросы и
  блокеры (`type: blocker`, заголовок `ВОПРОС`/`БЛОКАТОР`/`ЖДЕМ`…) — содержание условия:
  их «Заблокировано» и отсутствие даты риском не считаются, их просрочка — считается;
- **В плане** — иначе. Запас — `due` минус самый поздний срок невыполненных зависимостей.

`lint`: ошибка — нет вехи `milestone` или целевого состояния `track`+`target`, `depends` на несуществующую
задачу, плохая дата; предупреждение — нет `owner` или `due`, `due` позже целевого состояния.

`report <папка> <id вехи>|<трек>@<дата>` — отчёт о рисках вехи или состояния (markdown; `--json` — для агента):
условия по тяжести, ответственные, сроки и запас, зависимости с причинами, просроченные
и заблокированные предшественники («что тянет назад»), разделы последствий и возврата к плану.

## Пакет руководству `.xlsx`

`bin/roadmap xlsx <папка> -o <out.xlsx> [--track N] [--goals 1,2,3,4] [--date ГГГГ-ММ-ДД]` — книга из четырёх листов
по одному треку (утверждённый PO формат выпуска 19.11.2026; код — `scripts/xlsx_pack.py`, только stdlib):

| Лист | Что на нём |
|---|---|
| «Roadmap» | трек, результат, цели по неделям: шапка Q / месяц / W1–W13 (неделя квартала), полоса окна цели, ★ — окончание цели, ◆ — окончание эпиков (номер, название, дата — в примечании ячейки); строка «Ключевые точки» — только у цели с датированными эпиками; нерабочие недели тёмные |
| «ГАНТТ» | Цель → Эпик → История → Задача: роль, кто делает, принимает, старт, финиш, статус, прогресс (курсивом с примечанием — расчёт по подзадачам, раздел «Журнал …»; у пункта DoD пусто), полоса по неделям цвета роли; строки сгруппированы (outline) до целей |
| «Реестр вопросов» | открытые вопросы трека: ожидаемый ответ (из «Комментария»), ответственный, срок (последнее «до ДД.ММ.ГГГГ»), критичность, на что влияет |
| «Беклог задач» | эпики и истории: цель, DoD, демо (HowToDemo), сроки, открытые вопросы |

- Уровни: задача верхнего уровня трека — Цель, её подзадача — Эпик, глубже — История; Задача — пункт
  `Definition of Done:` истории (или эпика без историй), наследует её сроки и исполнителя.
- **Даты на «ГАНТТ» и в «Беклоге» — только если `estimate: подтверждена` у самой задачи (оценка команды) или
  `status: Выполнено`**; иначе ячейки пустые. На «Roadmap» окна целей и ◆ эпиков — по датам карты.
- Номер — из начала `title` («1.2 …»); нет — родитель.k по `ordinal`. Цель без номера — по порядку в треке.
- Тексты для руководства (`clean`): из скобок убираются коды WBS, номера задач плана, ссылки на созвоны и страницы
  Confluence, даты; номера вопросов Q-NN остаются. «(1.1.1, П-1.4, Q-07)» → «(Q-07)».
- `--goals` — цели на листе «Roadmap»; по умолчанию — все цели трека, у которых есть эпики. `--track` — номер трека
  сборной карты; по умолчанию — первый свой трек; у одиночной папки трек один. `--date` — дата подписи реестра
  вопросов (по умолчанию сегодня).
- Печать: альбомная A3 по ширине страницы, шрифт Arial. Одинаковые данные — байт в байт одинаковый файл.
- `bin/roadmap letter <папка> -o <letter.txt> [те же параметры] [--xlsx <имя вложения>]` — текст письма руководству.
  Тема — из `title` карты (паспорт сборной карты или папки) без хвоста « — целевые состояния»: «Цель 01 «…», стрим
  «<трек>» — предварительный Roadmap и открытые вопросы». Кто оценил сроки — по каждой цели исполнители (`assignee`)
  самых мелких задач с `estimate: подтверждена`: «(по цели 1 — <исполнители>)»; оценок нет — без скобок.

Кнопка «Экспортировать в .xlsx» на странице отдаёт этот же файл, собранный при `build` и встроенный в html: первый
свой трек (у сборной карты — трек с меньшим номером), цели с эпиками, дата — последняя дата данных карты (история
вопросов, журнал, комментарии задач), поэтому сборка не зависит от дня запуска. Правки, сделанные на странице и не
перенесённые в md, в файл не входят. Другой трек — `bin/roadmap xlsx <папка> --track N`.

## Дейлик: `reports/daily/ГГГГ-ММ-ДД.md`

`bin/roadmap daily <папка цели или стрима> --date ГГГГ-ММ-ДД [--since ГГГГ-ММ-ДД] [-o <файл.md>]` — один запуск, один
отчёт markdown о продвижении к целям за период (код — `scripts/daily.py`, только stdlib). Карта должна проходить `lint`
без ошибок. Навык — `roadmap-11-daily`, промпт расписания — `templates/daily-brief.md`.

- **Файл** по умолчанию — `<корень>/reports/daily/<дата>.md`, где корень — папка над `.okr/` (карта вне `.okr/` —
  сама папка карты). В конце файла — пометка `<!-- roadmap daily · карта: <путь> · дата: … · период с: … -->`: по ней
  команда отличает отчёты разных карт в одной папке.
- **Период** — дни после `--since` по `--date` включительно. По умолчанию `--since` — дата последнего отчёта этой карты в
  папке отчётов раньше `--date` (имя `ГГГГ-ММ-ДД.md`), нет такого — `--date` минус 7 дней. Запись журнала — в периоде,
  если её день (`Дата` без времени) в нём; записи позже `--date` не учитываются.
- **Перезапись.** Отчёт за ту же дату пересобирается (тот же период). Отчёт, после которого уже есть более поздний, и
  файл дейлика другой карты команда не перезаписывает — ошибка.
- **Детерминированность.** Одинаковые файлы карты и параметры — байт в байт одинаковый отчёт; текущего времени и
  абсолютных путей в нём нет, ссылки — относительно файла отчёта. Отчёт за прошлую дату собирается по данным на ту дату:
  журнал — записи не позже неё, реестр — вопросы, заведённые к ней (первая датированная строка «Истории»), закрытые к
  ней — по строке «Готово» в «Истории» или записи журнала о вопросе со статусом «Готово».

**ЦС и шаги.** ЦС — задача верхнего уровня своего трека (без `parent`; как «Цель» листа «ГАНТТ»), в порядке страницы;
шаги — её подзадачи. Блокеры (`type: blocker`) и задачи `ВОПРОС`/`БЛОКАТОР`/`ЖДЕМ`/`ВЛИЯЕТ`/`РИСК` не ЦС и не шаги:
они попадают в риски. Номер — из нумерации трека, иначе из начала `title` («1.1 …»), иначе по порядку. У сборной
карты — раздел на каждый трек (стрим), ссылки ведут в файлы папки стрима.

**Прогресс задачи на дату** (правило расчёта; в md ничего не добавляется):

1. статус «Выполнено» на дату — 100%;
2. иначе свой прогресс: последняя запись «прогресс» журнала не позже даты (её Статус — статус задачи); записей нет —
   `progress` из md («md»);
3. своего нет — среднее по подзадачам, которые входят в прогресс (без блокеров и ВОПРОС/РИСК…), с округлением половины
   вверх — «расчёт по подзадачам: N»; так считается прогресс шага и ЦС, если PO не назвал свой (то же правило — на
   странице и в .xlsx);
4. подзадач нет — 0% («нет записей»).

Если у задачи записи журнала есть только позже даты, её прогресс и статус до первой записи неизвестны: в расчёте —
пункт 3 или 4. **Изменение за период** — «было → стало»: то же правило на `--since` и на `--date`.

**Разделы отчёта:**

| Раздел | Что в нём |
|---|---|
| Заголовок | «Дейлик ДД.ММ.ГГГГ — <title карты без « — целевые состояния»>», период и откуда он взят, папка карты |
| **Итог** | одна фраза из данных: записей журнала (прогресс, комментарии), у скольких ЦС изменился прогресс (было → стало), вопросов закрыто и новых, риски счётом; ничего не менялось — «изменений за период нет: …» и риски |
| `## Трек N. Название` | папка стрима, ссылки на `questions.csv` и `journal.csv` |
| `### ЦС N · <id> — <название>` | прогресс (откуда), за период было → стало, статус; срок, исполнитель, файл; ближайшая веха — самая ранняя дата впереди: веха внутри ЦС, финиш шага или финиш ЦС |
| Шаги | номер, ссылка на файл, статус, прогресс (откуда), срок, исполнитель, изменение за период |
| Что изменилось за период | записи журнала о задачах ЦС и её вопросах: дата, объект, «прогресс было → стало, статус» или «комментарий», текст, автор |
| Вопросы | всего, открыто, критичных, без ответственного, закрыто и новых за период; списки: закрытые (с ответом), новые, открытые критичные (ответственный, срок), без ответственного. Вопрос — у каждой ЦС, на задачи которой влияет |
| `## Риски` | просроченные задачи (финиш раньше даты, не «Выполнено»), заблокированные (с последней записью журнала о блокировке), вопросы с прошедшим сроком ответа |
| `## Следующие шаги — до ДД.ММ.ГГГГ` | старты и финиши задач и сроки ответов в окне `--date`…`--date`+7 дней, ближайшее целевое состояние паспорта |
| `## Вопросы к PO на завтра` | только из данных: открытые критичные без ответственного; просроченные ответы; задачи окна без исполнителя; вопросы агента — комментарии журнала с Автором «агент» и Текстом «Вопрос PO: …», пока о том же объекте нет более поздней записи не от агента |
| Как считано | правило прогресса, сроков и срока ответа одним абзацем |

**Даты.** Сроки задач — как на карте; без даты — «срока нет»; у задачи без своего `estimate: подтверждена` (и не
выполненной) — пометка «(оценки нет)». Правило пакета руководству «даты только по оценке команды» в дейлике не
скрывает даты: отчёт для PO и команды; пометка показывает, где оценки нет. **Срок ответа** вопроса — последнее
«до ДД.ММ.ГГГГ» в «Комментарии» и «Истории» (тот же разбор, что у листа «Реестр вопросов»); пишите «Срок ответа: до
ДД.ММ.ГГГГ».

## `roadmap.json`

Пишет `lint`: этапы с номерами и составом, условия (`conditions`: цель, срок, ответственный, зависимости), по каждой задаче — номер, файл, родитель,
этап, тип, статус, роль, даты, `after` (от чего зависит) и `before` (что ждёт её,
с раскрытием зависимостей на этапы), предупреждения. Для агента — быстрый ответ на
«что сдвинется, если сдвинуть X».

## Страница и комментарии

`roadmap.html` — один файл без внешних запросов: обзор треков, страница своего трека
с этапами или ролями, карточка задачи, кнопка «Экспортировать в .xlsx» (пакет руководству, собранный при `build`, —
раздел «Пакет руководству `.xlsx`»). Правки мышью (даты,
статусы, порядок, новые задачи) хранятся в браузере и в md сами не попадают.

Комментарии к задачам и вопросам и смена прогресса или статуса задачи — ещё и записи несохранённого журнала:
«Экспортировать» дописывает их в `journal.csv` своих папок в архиве (раздел «Журнал комментариев и прогресса»).
Журнал браузера у каждого зрителя свой: опубликованная страница без общей базы не синхронизирует его между людьми.

Верхняя панель — канал правок для агента: правый клик по любому элементу карты
(задача, этап, трек, роль, целевое состояние, неделя в шапке) или режим
«Комментировать» → комментарий. «Скопировать промпт» отдаёт одним сообщением все
комментарии (с адресом: номер, файл, неделя), все правки, сделанные на странице, и строки для `journal.csv`.
Агент вносит их в md и пересобирает страницу; после пересборки правки страницы
сбрасываются — они уже в md.
