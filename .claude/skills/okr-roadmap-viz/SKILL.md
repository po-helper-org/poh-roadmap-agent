# Навык: Roadmap цели — md → граф → html

## Использование

```
/okr-roadmap-viz <slug|папка> [что сделать]
```

`<slug>` — короткое имя цели латиницей (`goal-01`), папка — `.okr/roadmap/<slug>/`.
Первый запуск собирает roadmap из наработок, следующие — правят его. Если PO вставил
промпт из панели комментариев страницы — это тот же навык, этап 4.

**Целевые состояния (ЦС) — по конституции.** Декомпозируешь или правишь ЦС — сначала прочитай
`resources/constitution.md` (принципы, статьи, порядок работы, чек-лист приёмки) и эталон ЦС1, на который она
ссылается. В стриме ЦС конституция старше этого навыка.

## На выходе

```
.okr/roadmap/<slug>/roadmap.md     паспорт — пишешь ты
.okr/roadmap/<slug>/backlog/*.md   задачи своего трека — пишешь ты
.okr/roadmap/<slug>/conditions/*.md реестр условий целевых состояний — пишешь ты
.okr/roadmap/<slug>/questions.csv   реестр вопросов и ключевых решений — пишешь ты (вопросы только из источников)
.okr/roadmap/<slug>/journal.csv     журнал комментариев и прогресса — дописываешь ты (строки PO со страницы, отметки о ходе работ)
.okr/roadmap/<slug>/roadmap.json   граф и номера — пишет lint
.okr/roadmap/<slug>/roadmap.html   страница — пишет build
```

Формат и проверки — `.claude/skills/okr-roadmap-viz/resources/format.md`. Эталон —
`.claude/skills/okr-roadmap-viz/scripts/fixtures/sample/`. Скрипт —
`.claude/skills/okr-roadmap-viz/scripts/roadmap.py` (в репозитории — обёртка `bin/roadmap`),
только Python 3:

```bash
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py init  .okr/roadmap/<slug> --title "Цель 01. …"
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py lint  .okr/roadmap/<slug>
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py tree  .okr/roadmap/<slug>
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py build .okr/roadmap/<slug>
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py questions .okr/roadmap/<slug> [<id задачи>] [--open]
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py report .okr/roadmap/<slug> [<id вехи>|<трек>@<дата>|goal@<дата>|all] [--today ГГГГ-ММ-ДД] [--json]
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py xlsx   .okr/roadmap/<slug> -o <out.xlsx>   [--track N] [--goals 1,2,3,4] [--date ГГГГ-ММ-ДД]
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py letter .okr/roadmap/<slug> -o <letter.txt> [--track N] [--goals …] [--date …] [--xlsx <имя вложения>]
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py daily  .okr/roadmap/<slug> --date ГГГГ-ММ-ДД [--since ГГГГ-ММ-ДД] [-o reports/daily/ГГГГ-ММ-ДД.md]
```

Запускай из корня воркспейса: путь к папке попадает в промпт, который страница
отдаёт агенту.

### Сборная карта цели из нескольких папок

Цель с несколькими стримами, у каждого — своя папка (`backlog/`, свой `questions.csv`): одна страница на всех —
папка цели с одним `roadmap.md`, где у каждого трека `- папка: ../<slug стрима>` (формат — `resources/format.md`,
раздел «Сборная карта цели из нескольких папок»; пример — `scripts/fixtures/goal/`).

```bash
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py lint  .okr/roadmap/<slug цели>    # проверяет каждую папку стрима
python3 <корень>/skills/okr-roadmap-viz/scripts/roadmap.py build .okr/roadmap/<slug цели> -o roadmap.html
```

- Правишь задачи и вопросы — в папке стрима, как обычно; пересобираешь — сборную папку (и одиночную страницу стрима,
  если она нужна). Паспорт цели — только треки, роли, выходные, целевые состояния цели.
- На странице id задачи — `<трек>:<id>`; в md пиши id из файла своей папки. Промпт со страницы даёт полный путь к
  файлу стрима.
- Общий вопрос (один ID в двух реестрах) на сборной странице один: тексты — из реестра без пометки «Общий вопрос…».
  Ответ пиши туда; копию обнови тем же текстом — иначе `lint` предупредит о расхождении.

### Восстановление из архива «Экспортировать»

Пришёл `<slug>-backup-<дата>.zip` — работай по его `RESTORE.md`: `map/` — источник истины (точные копии md и
`questions.csv`), `PENDING.md` — правки PO из браузера, ещё не внесённые в md (перенеси их первыми), `context.json` — быстрый
обзор, `tool/` — сборщик, если этого репозитория нет: `python3 tool/okr-roadmap-viz/scripts/roadmap.py build map`.
`journal.csv` в `map/` (у сборной карты — в папке каждого стрима) уже содержит в конце комментарии и прогресс PO со
страницы: перенеси журнал в репозиторий — допиши в конец `journal.csv` своей папки строки, которых там ещё нет (по
порядку, не меняя), а не пересказывай их в md.

### Журнал комментариев и прогресса (`journal.csv`)

Комментарии PO о ходе работ и прогресс задач ведутся в `journal.csv` папки стрима (формат — `resources/format.md`,
раздел «Журнал комментариев и прогресса»): `Дата;Объект;Тип;Прогресс;Статус;Текст;Автор`, Объект — id задачи из
`backlog/` этой папки или Q-NN её `questions.csv`. Для новых комментариев это основной способ; раздел «## Комментарии»
в md задачи старый — читается как раньше, новых строк туда не пиши, существующие не переноси без просьбы PO.

- Строки только **дописываешь в конец** файла (UTF-8 с BOM, CRLF), старые не правишь и не удаляешь. Комментарий PO —
  его словами, Автор пусто (PO) или кто сказал; дату не выдумывай — с созвона или из промпта.
- Прогресс задачи — строка «прогресс» (0…100 и статус). Последняя по дате запись задаёт прогресс и статус на странице;
  frontmatter `progress`/`status` обнови тем же значением, иначе `lint` предупредит о расхождении.
- Комментарий PO — это ещё и поручение: если он просит изменить план (дату, статус, задачу, вопрос), сделай правку в md
  или `questions.csv` по этапу 4 и, если нужно, ответь строкой «комментарий» с Автором «агент».
- Строки «Журнал …» из «Скопировать промпт» или `PENDING.md` — готовые строки CSV: допиши их как есть в указанный
  файл; строка, которая там уже есть, не повторяется (страница узнаёт свои записи по Дате, Объекту, Типу, Прогрессу и
  Тексту).

## Принцип

Три шага, у каждого свой исполнитель:

| Шаг | Кто | Что |
|---|---|---|
| Декомпозиция | ты (LLM) | Наработки → `roadmap.md` и `backlog/*.md`: треки, этапы, задачи, даты, роли, зависимости, вехи, блокеры, вопросы |
| Проверка и граф | `roadmap.py lint` | Схема, ссылки, циклы, порядок дат по зависимостям, номера 3.7.1 → `roadmap.json` |
| Визуализация | `roadmap.py build` | Один `roadmap.html` из md по шаблону. Одинаковые md — байт в байт одинаковая страница |

Ты работаешь только с md. В html и json руками не лезешь: номера, недели, порядок,
полосы и стрелки считает скрипт. Вид страницы зашит в шаблон
`scripts/assets/` — его не правят под конкретную цель.

## Инструкция для LLM

### Правило источников (главное)

В md, `questions.csv` и `conditions/` пишется только то, что есть в источниках: слова PO,
документы, выгрузки, WBS, ответы людей. Не придумывай вопросы, сроки, ответственных,
утверждающих и критерии. Нет источника — поле пустое, а в тексте сказано «не назначено»
или «в источниках нет». Своё предложение помечай в «Комментарии» как «предложение агента»
и спрашивай PO, прежде чем выносить на страницу. Источник каждого вопроса — в «Комментарии»
`questions.csv`.

### Этап 0: Вводные

1. Папка `.okr/roadmap/<slug>/` есть → прочитай `roadmap.md`, запусти `tree`: это
   текущее дерево с номерами, файлами и зависимостями. Дальше — этап 2 или 4.
2. Папки нет → собери наработки: что PO приложил или назвал (выгрузка GanttPRO,
   `.xlsx`/`.csv`, заметки, `.okr/<quarter>/plan/scope-*.json`, `teamplanner-*.json`,
   эпики Jira, Confluence), плюс разговор. Индекс воркспейса — `.okr/index/`.
3. Спроси PO только то, без чего не собрать, одним сообщением, не больше трёх
   вопросов: название цели, какой трек свой (раскладывается на задачи), что брать
   из источников, если они спорят. Остальное — бери из наработок.

### Этап 1: Декомпозиция в md

1. `roadmap.md` по формату: роли, выходные недели, целевые состояния цели, все треки.
   У чужих треков — результат, план по ролям, целевые состояния. У своего — `- свой: да`,
   `- нумерация: <N>` (номер цели или трека, как PO привык: 3 → 3.1, 3.7.1) и этапы.
2. Каждая задача своего трека — файл `backlog/task-<N> - <название>.md`. `id` —
   `task-1`, `task-2` … подряд; при импорте можно сохранить id источника (`t84`,
   `ABC-123`). id не переиспользуй и не меняй: на них держатся зависимости и
   комментарии.
3. Что известно — пиши; чего нет — оставь пустым. Даты, людей и проценты не выдумывай.
   Неизвестное, которое надо решить, — подзадача `ВОПРОС: …` со статусом
   «Заблокировано»; то, что мешает, — `type: blocker` с датой, когда снимется.
   Контрольные точки «готовы к …» — `type: milestone`.
4. Порядок — `ordinal` шагом 10 (10, 20, 30), чтобы потом вставлять между.
5. Номера (3.7.1) в `title` не пиши — их ставит скрипт. Сослаться на задачу в
   названии — `{#task-12}`.
6. Больше 20 задач — пиши файлы коротким скриптом из разобранного источника, а не по
   одному: так меньше опечаток в полях.
7. Есть функциональная декомпозиция (WBS из MS Project / GanttPRO XML, дерево фич) —
   это второе измерение тех же работ, а не новые задачи. Сначала сопоставь её с
   этапами и покажи PO таблицу «ветка → этап и задачи» с пробелами в обе стороны.
   После согласования: дерево — в `### Фичи` своего трека (2–3 уровня), задачам —
   `feature:`. Узел без своих сроков — подзадача существующей задачи с её окном и
   пометкой «оценки нет»; листья — чек-листом в теле файла. Решения — `type: blocker`
   с датой «пятница перед стартом зависимой работы», результаты — вехи с датой
   финиша работы, от которой зависят. Даты, которых нет ни в одном источнике, не
   выдумывай.

### Этап 2: Проверка

1. `lint`. Ошибки исправь в md и повтори, пока не «Принято». Своими словами
   ошибку не обходи: не удаляй зависимость, чтобы убрать цикл, — спроси PO, какая
   из связей лишняя.
2. Предупреждения о датах по зависимостям — покажи PO списком: это либо опечатка в
   дате, либо реальное нарушение плана. Молча даты не сдвигай.
3. `tree` — сверь дерево с источником: все ли задачи на месте, правильно ли
   вложены, верны ли номера относительно того, к чему привык PO.

### Этап 3: Сборка

`build` → `roadmap.html`. Отдай файл PO (или путь к нему) и одной строкой скажи,
что в нём: треков, этапов, задач, со сроками, предупреждений.

### Пакет руководству: `xlsx` и `letter`

Когда PO просит Roadmap для руководства, «выгрузку в xlsx», ГАНТТ или беклог файлом — после `lint` без ошибок:

1. `xlsx <папка> -o <файл.xlsx> --date <сегодня>` (у сборной карты — `--track N`; `--goals` — какие цели на листе
   «Roadmap», по умолчанию цели с эпиками). Формат зафиксирован (выпуск 19.11.2026): четыре листа «Roadmap»,
   «ГАНТТ», «Реестр вопросов», «Беклог задач» — `resources/format.md`, раздел «Пакет руководству `.xlsx`».
   Руками файл не правь: нужна другая подача — правь md и собирай заново.
2. `letter <папка> -o <письмо.txt> --date … --xlsx <имя файла.xlsx>` — текст письма к вложению.
3. Даты на «ГАНТТ» и в беклоге появляются только у задач с `estimate: подтверждена` (срок оценила команда — по словам
   команды или PO, правило источников) или выполненных. Не ставь `подтверждена`, чтобы «появились даты».
4. Отдай PO путь к файлу и одну строку: целей, эпиков, историй, задач, открытых вопросов (печатает команда).

Тот же файл встроен в страницу при `build` — кнопка «Экспортировать в .xlsx» (первый свой трек, по данным сборки).

### Дейлик: `daily`

PO просит ежедневный отчёт или идёт запланированная сессия с промптом `templates/daily-brief.md` — навык
`roadmap-11-daily`: данные — в журнал и реестр, затем `daily <папка> --date <сегодня>`. Один запуск — один файл
`reports/daily/<дата>.md`; формат и правило расчёта прогресса — `resources/format.md`, раздел «Дейлик». Отчёт руками не
правь.

### Этап 4: Комментарии со страницы

На странице PO комментирует любой элемент карты (правый клик или режим
«Комментировать»), двигает даты и строки мышью, добавляет задачи. «Скопировать
промпт» отдаёт всё одним сообщением: пронумерованные комментарии с адресом (номер,
файл, неделя) и список правок, сделанных на странице.

1. Правки страницы переноси в md как есть: даты, статусы, роли, зависимости —
   в поля файла; новая задача — новый файл со следующим `task-<N>`; новый порядок —
   `ordinal` по порядку; перенос — `parent`/`stage`; комментарий о состоянии и прогресс —
   строка в `journal.csv` папки задачи (раздел «Журнал комментариев и прогресса» выше).
2. Комментарии — по одному: что просят, в каком файле, что меняешь. Неясно — не
   угадывай, вопрос PO в отчёте.
3. Номера в промпте — на момент той сборки; ищи задачу по файлу или id, не по номеру.
4. `lint` → `build`. После пересборки правки страницы в браузере сбрасываются сами —
   они уже в md. Комментарии PO очищает кнопкой, когда прочитает отчёт.

### Этап 5: Реестр условий и отчёт о рисках целевого состояния

Условие — то, без чего целевое состояние не наступит к сроку: решение бизнеса,
согласование, готовая работа. Одно условие — один файл `conditions/<id> - <название>.md`
(формат — `resources/format.md`, раздел «Реестр условий»), привязан к вехе (`milestone:`)
или целевому состоянию. На странице — вкладка «Реестр» в карточке вехи и страница
«Реестр условий»: условия каждого целевого состояния, ответственные, сроки, зависимости
и вычисленное состояние (в плане / в зоне риска / сорвано / выполнено).

1. Заводи условия, когда PO спрашивает «на чём держится срок»: у каждого — `owner`,
   `due` (крайний срок, после которого цель сдвигается), `depends` (задачи, которые должны
   закончиться к `due`; вехи **после** `due` — это последствия, их не ставь) и три
   раздела: «Что должно произойти», «Если сдвигается» (что и на сколько сдвинется),
   «Чтобы вернуться к плану». Числа сдвига бери из графа (`roadmap.json`: `before`), не угадывай.
2. Просят отчёт о рисках по целевому состоянию → `report <папка> <трек>@<дата>`. Отчёт
   детерминирован: состояние условий, просроченные и заблокированные задачи-предпосылки,
   тексты последствий. Поверх него ответь тремя разделами: **что в зоне риска** (условия,
   задачи, кто отвечает), **последствия** (что и на сколько сдвинется), **что нужно, чтобы
   вернуться к плану** (действие · кто · к какой дате). Не пересказывай весь отчёт — выводы
   и ссылки на `conditions/<id>`.

## Отчёт

```
Roadmap «<цель>»: .okr/roadmap/<slug>/roadmap.html
Треков N, этапов N, задач N (со сроками N), зависимостей N. Предупреждений: N.

По комментариям: 1 — сделано (<файл>), 2 — вопрос: <…>, …
Правки страницы: перенесено N.

── СТОП ── Откройте страницу. Новые правки — комментариями и «Скопировать промпт».
```
