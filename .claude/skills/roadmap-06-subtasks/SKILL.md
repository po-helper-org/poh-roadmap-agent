# Этап 6. Подзадачи с ролями исполнения и эталон

Цель этапа — понятный объём каждого шага: кто делает, кто принимает, что покажут на приёмке. Шаблоны подзадачи и шага —
`templates/backlog/`; правила — `constitution.md`, статьи II.3–II.5, IV.3, VI. Прочитай эталон перед первым файлом:
`examples/school-migration/.okr/roadmap/courses/backlog/` (`w1-1-1`, `w1-2-1`, `s14-1`, `s21-1`) или эталон своего
проекта.

## Делаешь

1. Раскладываешь пункты WBS (`sources/wbs.tsv`) и задачи плана по шагам: лист WBS → подзадача `w<код>`; задача плана
   вне WBS → `s<N><k>-<n>`; агрегат подзадачей не делаешь; пункт «принять решение / нужен ли вообще» → новый вопрос
   реестра, а не подзадача. Пункт, который не лёг никуда, — пробел PO.
2. Показываешь PO таблицу «шаг → подзадачи → роль → исполнитель → принимающий» до записи.
3. Пишешь файлы снизу вверх: подзадачи → DoD и HowToDemo шага из подзадач → DoD и HowToDemo ЦС из шагов.
4. У подзадачи: `role` из «## Роли» по виду работы; `assignee` — команда техлида зоны («для техлида А — Команда А»);
   `approver` — только если задан PO. Разделы AS-IS, GAP (с `Q-NN`), TO-BE, DoD, HowToDemo — по 1–2 строки про приёмку.
5. Бизнес-подзадачи шага решений (решения, спецификация) — с исполнителями от бизнеса, только если PO так решил.
   **Технический шаг на стыке двух систем** (интеграция контура А и платформы Б) раскладывай в порядке
   «аналитика → проектирование → доработки обеих сторон» (рекомендация): аналитика (SA: маппинг полей, сценарии,
   ограничения) → проектирование (контракт обмена, согласование архитектуры обеими сторонами) → доработка стороны А и
   доработка стороны Б (отдельные подзадачи, исполнитель — команда своей зоны) → совместная проверка. Подзадачи — по-
   прежнему только из WBS и плана: пункта нет — предлагаешь его «предложением агента» и пробелом PO, а не заводишь.
6. Сроки — только из плана, оценки команды (`estimate: подтверждена`) или от PO. Родитель не короче подзадач:
   растягиваешь по датам PO или плана, конфликт — PO.
7. `lint` → `check-qlinks` → `build`; разбираешь каждое предупреждение.

## Эталон и поправки (после первого ЦС)

1. Проходишь чек-лист конституции по ЦС; PO говорит «фиксируем как эталон».
2. Решения PO, которые расходятся с конституцией, записываешь поправками с датой в раздел «Поправки» `constitution.md`.
3. Отступления эталона перечисляешь в статье VIII, чтобы их не копировали.
4. Следующие ЦС раскладываешь по эталону. Несколько ЦС сразу — рой: `templates/workflows/decomposition-workflow.js`
   (черновик на цель → два скептика → синтез → сквозная проверка и критик, только чтение), затем
   `apply-workflow.js` (сведение по единым правилам → реестр → запись карты → проверки и коммит). Агенты, которые
   **пишут** файлы, работают каждый в своей рабочей копии (git worktree или ветка), а не в общей папке: ты сливаешь их
   результат по очереди, после каждого слияния — `lint`, `check-qlinks`, коммит. Без Workflow — те же роли проходами
   по очереди (ручной режим, `roadmap-05-completeness`).

## Промпты PO

```
Декомпозируй шаги <N.1>…<N.k> на подзадачи из <WBS / плана> с конкретными ролями исполнения.
Исполнитель — команда техлида: у <техлид А> — <команда А>, у <техлид Б> — <команда Б>; принимает — <кто>.
Для подзадач: AS-IS, GAP, TO-BE, DoD, HowToDemo — просто и кратко, что ожидается на приёмке.
```

```
Зафиксируем разбор ЦС <N> как эталонный для всех будущих агентов: структура, декомпозиция, связи, наполнение.
Сверь с конституцией, мои решения, которых там нет, запиши поправками с датой.
```

## Ошибки, которые PO поправлял

- Исполнитель по догадке → только из зон, названных PO; нет — пусто и пробел.
- Подзадачи вне окна шага → «верхняя задача не может быть короче её подзадач».
- В названии тип («Блокатор: …») → «нужна суть сразу».
- Шаг растянут подзадачей со старым окном после того, как PO сдвинул шаг → сверяй окна потомков после каждой правки
  дат.
- Технический шаг разложили только на доработки одной стороны → аналитика → проектирование → доработки обеих сторон.
- Параллельные пишущие агенты правили одни и те же файлы и затирали друг друга → у каждого своя рабочая копия, слияние
  по очереди.

## Готово, когда

- [ ] Каждый пункт WBS цели — подзадача, пункт DoD или пробел PO
- [ ] `role` из «## Роли», исполнитель — команда техлида, принимающий — из зон PO или пусто
- [ ] AS-IS, GAP (с `Q-NN`), TO-BE, DoD, HowToDemo — по 1–2 строки, про приёмку
- [ ] Пункты «принять решение» стали вопросами реестра
- [ ] Родитель не короче подзадач; конфликты дат вынесены PO
- [ ] Чек-лист конституции пройден; `lint` — «Принято»; `check-qlinks` — 0; коммит
- [ ] После первого ЦС: PO объявил эталон, поправки записаны с датой
