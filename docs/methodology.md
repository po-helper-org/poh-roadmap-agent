# Методология: Roadmap целевых состояний вместе с Claude Code

Документ для человека, который ведёт планирование (PO — владелец цели). Агенту хватает навыков в `.claude/skills/`;
сюда он заходит за примерами и объяснениями.

Методология выведена из реального проекта: перевод продаж с одной платформы на другую. В проекте было восемь
целевых состояний, после слияний и выделения отдельного стрима осталось шесть; участвовали технические, продуктовые
и бизнес-команды двух компаний и управляющий комитет, а неопределённость была в договорах, деньгах и технике. Работа
заняла три дня диалога PO с агентом, около 70 коммитов и больше сотни реплик PO. Всё обезличено: компании — «контур А»
(старая система) и «платформа Б» (целевая), люди — ролями, суммы и бренды убраны. Сквозной пример с вымышленным
доменом — `examples/school-migration/`.

Где обобщение выходит за то, что было в проекте, стоит пометка «(рекомендация)».

к нему PO пришёл на ЦС2. На ЦС1 подзадачи появились раньше вопросов, и их GAP потом переписывали (рекомендация).

## Принципы

1. **Только из источника.** Можно: слова PO, документ в `sources/`, ответ названного человека. Нельзя: выдумывать
   вопросы, сроки, ответственных, критичность, эскалации. Нет источника — поле пустое, в тексте «в источниках не
   описано». Вывод агента допустим, но помечен «предложение агента», показан PO и внесён только после «да».
2. **PO решает, агент предлагает.** Формулировку цели, имя ответственного, срок, критичность, границу цели и вариант
   решения выбирает PO. Агент приносит таблицу, варианты с рекомендацией и пробелы.
3. **Путь объекта, а не список компонентов.** Декомпозиция понятна, когда видно, как один объект проходит путь по
   системам и что должно быть истинно на каждом шаге.
4. **Один документ — три глубины.** ЦС читает руководитель («будет ли и когда, что мешает»), шаги — все («что должно
   заработать»), подзадачи — аналитик и команды («что сделать, кто, к какому сроку»).
5. **Шаг — измеримый результат.** Проверяется словом «да» к дате. Работа, решение и критерий приёмки шагом не бывают.
6. **Вопросы живут в реестре.** Точечный вопрос, ожидаемый ответ, источник, «Влияет на», ответственный, срок, статус,
   история. На Ганте видно только число вопросов у задачи.
7. **У срока есть основание.** Каждая дата держится на плане, оценке команды, слове PO или окне родителя. Оценки
   команды нет — это видно на полосе. Родитель не короче подзадач.
8. **Сборка детерминирована.** Страницу, .xlsx и письмо строит скрипт из md и csv: одинаковые файлы — байт в байт
   одинаковый результат. Всё, что набрано руками, сверяется с картой перед отправкой.
9. **Такт.** Одна реплика PO и один цикл: предложение → «да» → md/csv → lint → build → коммит → отчёт с пробелами.
10. **Ничего не теряется.** Коммит после каждого такта; реплики PO в `sources/po-messages.md`; журнал комментариев в
    `journal.csv`; бэкап по запросу и перед сменой инструмента; `HANDOFF.md` для следующего агента.

## Этапы подробно

Формат каждого этапа: зачем, как было, ошибки агента и как их избежать. Вход, выход, промпты и чек-лист — в навыке
этапа (`.claude/skills/roadmap-NN-*/SKILL.md`).

### Этап 0. Источники и рамка — `roadmap-00-sources`

**Зачем.** Принцип «только из источника» работает, только если у каждого источника есть файл: выгрузка WBS и её чистая
таблица, план трека, реплики PO, состав команды словами PO, позже — архив рабочих созвонов и сводка документации.

**Ошибки агента.**
- Наивный парсинг XML Ганта сдвинул коды WBS относительно названий на одну позицию → сопоставляй поля внутри одного
  узла, держи `wbs.tsv`.
- Номер вехи плана взят из промежуточной модели агента, а не из Ганта PO. Ошибку нашёл фактчек → номера и даты плана
  сверяй только с исходником PO.

### Этап 1. Цели словами PO — `roadmap-01-goals`

**Зачем.** Начать с чистого листа: на карте только цели PO и их даты.

**Как было.** PO продиктовал 8 целевых состояний и попросил «чистый артефакт, в котором отображены только целевые
состояния и их даты».

**Ошибки агента.**
- Перерисовал интерфейс в другом стиле («Очень перемудрённая диаграмма»), потом сделал артефакт не в том дизайне →
  один инструмент и один вид страницы; вид меняется только комментарием PO.
- Завёл реестр условий по всем трекам, когда PO интересовал один стрим → начинай с минимума, который PO назвал.

### Этап 2. Путь объекта — `roadmap-02-path`

**Зачем.** «Я не понимаю, что именно нужно сделать, чтобы всё завелось и заработало». Список работ по компонентам
этого не показывает, путь одного объекта — показывает.

**Как было.**
- Агент перестроил ЦС1 в путь одного объекта от внешней системы до витрины и показал «мини-версию» на трёх уровнях.
  PO: «Давай сейчас заведём уровень 2 на Roadmap».
- Для ЦС2 PO задал другой ракурс: «сверху вниз легко читался план работ для представителей бизнеса… всё, что с
  цифрой, — бизнес-ценная единица с измеримым результатом». Агент предложил 10 шагов, PO внёс три правки, осталось 9.

| Было у агента | Правка PO | Правило |
|---|---|---|
| Шаг «Приёмка: заказчик видит результат» | удалить | Приёмка — пункт DoD цели |
| Шаг «Изменения у источника доходят до платформы» | «это пункт просто один из DoD» | Свойство результата — DoD |
| Шаг «Решения до старта разработки» с блокаторами-вехами | вопросы в реестр, «блокаторы убрать из Ганта» | Решение — вопрос в реестре |
| Шаг «Данные уходят в учётную систему» | «убери, это инструмент, и не обязательно он будет использоваться» | Инструмент не входит в результат шага |
| Шаг «Билеты и чеки по требованиям» | «это условие для старта продаж, а не отдельный этап» | Условие старта — DoD соседнего шага |
| Шаг «Особые условия продаж работают» | «открытый вопрос, нужны ли они вообще» | Сомнительный объём — вопрос, шаг «если нужны» |
| PO в комментарии: «утвердили» | — | Агент не поставил «Выполнено», а спросил кто, когда, где. Статус — по доказательству |

**Плохо → хорошо.**
- Плохо: «Сделать API поиска справочников». Хорошо: «1.3 Справочники черновика сопоставлены с платформой Б».
- Плохо: «Договорная схема». Хорошо: «2.1 Бизнес обеих компаний утвердил правила расчётов и договорную схему».
- В примере: «1.2 Курс сохраняется черновиком и проверяется методистом в платформе Б».

### Этапы 3–4. Реестр вопросов — `roadmap-03-questions`

**Зачем.** Ответ на «на чём держится срок» — список вопросов, без ответа на которые шаг не стартует, с ответственным и
сроком у каждого. «Вот когда эти ответы получим — можем быть уверены, что бизнес всё утвердил и мы больше от них ничего
не ожидаем». Это возможно, только если каждый вопрос закрывается одним конкретным ответом.

**Как было.**
1. PO попросил ключевой блокатор цели и блокаторы в каждом шаге, «вопросы точечные, по доменам: к бизнесу, к продукту,
   к технарям».
2. Агент сочинил 9 вопросов, ответственных, срок и эскалацию. PO: «Что за бред — откуда ты вообще эти вопросы взял?»
   Три вопроса были придуманы целиком, остальные — пересказ слов аналитика.
3. Решение PO: «отдельный .csv… самодостаточная таблица (этап, вопрос, ответ, ответственные, влияет на, комментарий)…
   добавляются к Roadmap связью через линтер».
4. Детализация: «непонятно, какой ответ ожидается… очень размазанный, нужна конкретика»; «договорная обвязка —
   абстрактный вопрос… нужно точное описание, какие поля в договоре, как они влияют на отчёты, взаиморасчёты,
   возвраты… по каждому из процессов»; «[тема другого стрима] не относится к нашему стриму».
5. Назначения PO: «все бизнес-вопросы — два бизнес-владельца, срок до 1-го числа»; «<аналитик> не может быть
   ответственным ни за один из вопросов».

**Ошибки агента.**
- Заполнял поля «для полноты» → пусто, пока не сказал PO.
- Ставил ответственным исполнителя-аналитика → ответственных назначает только PO.
- Ошибался в написании имён → сверяй с PO и меняй во всех материалах сразу.

Правила вопроса и примеры «плохо → хорошо» — `.claude/skills/roadmap-03-questions/resources/questions-registry.md`.

### Этап 5. Полнота и ценность — `roadmap-05-completeness`

**Зачем.** PO спрашивал прямо: «реестр полный и достаточный? Получив ответы на все — можно считать аналитику
завершённой и достигнуть цели?» Ответить можно только честно и по шагам.

**Как было.**
- Самопроверка по одному шагу: пять тем из плана не попали в реестр.
- У четырёх шагов цели вопросов не было вовсе.
- Технический блок: из 41 вопроса 39 бизнесовых, не хватало восьми технических и одного блокатора доступа.
- Главный вопрос цели («какие партнёры уже интегрированы и кому нужен наш продукт — полный конечный список») первым
  назвал PO, а не агент.
- Ценность: 3 слияния, 2 снятия, 1 перенос в другую цель, 1 разделение.
- Рой: аудитор на каждый шаг, по два скептика на каждый пробел, 5 сквозных проверок, критик полноты. Вердикт:
  «окончательным признать нельзя», дальше «внесу механически» и «решить PO» с рекомендацией.

**Ошибки агента.**
- Перекос в бизнес-вопросы → отдельный проход по технике.
- Пропущен главный вопрос цели → на каждую цель: «какой ответ, если он изменится, переворачивает все остальные?»
- Соблазн сказать «да, полный» → полнота всегда «относительно источников»; ответы закрывают аналитику, цель
  закрывает работа.

**Когда звать рой.** На «окончательное решение» и «проверь полноту роем»; перед фиксацией эталона (несколько
независимых аналитиков эталона и проверяющих правил); при параллельной декомпозиции нескольких целей; перед отправкой
руководству (фактчек); для подбора ответственных и топ-3 вопросов (предложение → оспаривание). Рой всегда только
читает; его вывод — кандидаты, решение за PO. Шаблоны — `templates/workflows/`.

### Этап 6. Подзадачи с ролями и эталон — `roadmap-06-subtasks`

**Зачем.** «Декомпозировать всё на фичи разработки с конкретными ответственными ролями исполнения», чтобы был
понятен объём каждого шага.

**Как было.**
- Пункты WBS и задачи плана разложены по шагам. Роли — из «## Роли»: PO, SA, BE, FE, DEVOPS (последнюю добавили,
  когда появилась инфраструктура).
- Исполнитель — команда техлида: «для техлида контура А — его команда, для техлида платформы Б — его команда».
  Принимающий — техлид или CTO по зоне.
- Бизнес-подзадачи шага решений получили исполнителей от бизнеса по слову PO.
- Пункты WBS «принять решение / нужен ли вообще модуль» стали вопросами реестра.
- PO: «зафиксируем первый разбор как эталонный для всех будущих агентов: структура, декомпозиция, связи,
  наполнение… Запиши конституцию». Решения, принятые позже, стали поправками конституции.
- Оставшиеся цели раскладывал рой по эталону: черновик на цель → два скептика (источники; полнота и ценность) →
  синтез → сквозная проверка и критик; затем сведение по единым правилам, реестр, запись карты, проверки и коммит.

**Ошибки агента.** Исполнитель по догадке; подзадачи вне окна шага; шаг растянут подзадачей со старым окном после
того, как PO сдвинул шаг → исполнитель только из зон PO; окно шага растягивается по датам PO или плана, конфликт — PO.

### Этап 7. Цели как бизнес-эффект, стримы — `roadmap-07-business-goals`

**Зачем.** Названия целей «по схемам продаж» были техническими, а для бизнеса «всё это одно и то же, отличаются только
нормой прибыли и отчётностью».

**Как было.**
1. Агент разобрал архив созвонов и документации, объяснил разницу схем таблицей с пометкой «подтверждено / мой вывод».
2. Выписал технические ограничения по каждой схеме, недостающие вопросы внёс в реестр.
3. Предложил варианты А/Б. PO выбрал вариант с отдельной целью для особой группы клиентов.
4. Правки PO: «не понятно, чем цель 2 отличается от 3» → таблица различий; упрощение до «X работают в ПО Б на прежних
   условиях», детали — в DoD и HowToDemo; одну витрину влили в цель другой.
5. «Давай выделим 4 пункт — за пределы [трека]. Отдельный стрим в большом Roadmap» → своя папка стрима, id задач
   прежние, номера заново; затем «одна страница Roadmap, оба стрима полностью раскрываются» → сборная карта цели.

**Плохо → хорошо.**
- Плохо: «В ПО Б готовы запустить продажи по схеме X с учётом всех требований оператора». Хорошо: «Организаторы
  оператора работают в ПО Б на прежних условиях».
- Плохо: «Продажи по схеме Y». Хорошо: «Действующие витрины платформы Б готовы продавать мероприятия оператора через
  ПО Б» плюс образ результата: «расширить репертуар действующих витрин, сохранив норму прибыли».
- В примере: «Действующие ученики продолжают обучение на платформе Б на прежних условиях» с образом результата
  «тот же урок, тот же срок, без новой оплаты».

### Этап 8. Комментарии PO и журнал — `roadmap-08-comments`

**Зачем.** PO работает со страницей: правый клик → комментарий → «Скопировать промпт», правки мышью. Комментарии и
прогресс должны переживать пересборку и передачу.

**Как было.** Сначала правки шли только промптом. Затем PO попросил «комментарии и прогресс — отдельным файлом к
задаче, собираться детерминированно из .zip» → у каждого стрима `journal.csv`: страница копит записи в браузере,
«Экспортировать» дописывает их в архив, агент переносит строки в конец журнала, сборка показывает их сразу.

**Ошибки агента.** Комментарии терялись в браузере; новые записи шли в «## Комментарии» md → только `journal.csv`,
строки только дописываются. В пробном запуске Codex написал свои скрипты для дописывания журнала и ответов → команды
`bin/roadmap journal add` и `bin/roadmap question answer`. Те же правила — для реплик PO в чате и комментариев к
опубликованному артефакту (таблица «сказал → куда» в навыке).

### Этап 9. Пакет руководству — `roadmap-09-leadership-pack`

**Зачем.** «Генеральный директор, читая диаграмму, должен точно видеть, что сроки реализуемы, ЕСЛИ всё движется так, и
понимать все риски, за каждым — ответственный и коммитмент».

**Правки PO по ходу проекта.**
- Письмо: «вообще непонятный язык, ИИ-слоп нечитаемый — проще, с нормальным tone of voice для руководства».
- Реестр для руководителя: «полная дичь, непонятная» → простые и измеримые критические решения с пояснениями.
- Письмо руководителям: что стартует в прямом влиянии PO, а что зависит от внешней команды.
- На полосах без оценки: «Оценка не подтверждена технической командой».
- Финальный формат («чтобы в будущем именно вот так отгружал артефакт .xlsx»): один .xlsx из четырёх листов —
  «Roadmap» (цели по неделям, ★ окончание цели, ◆ окончание эпиков), «ГАНТТ» (Цель → Эпик → История → Задача),
  «Реестр вопросов», «Беклог задач».
- «По цели 1 есть оценки команды и сроки завершённых работ — их нужно отразить» → даты на «ГАНТТ» и в беклоге только у
  задач с оценкой команды или выполненных.
- Из названий и требований убраны коды WBS, номера задач плана и ссылки на созвоны; номера вопросов остались.
- Из письма убран блок «Что нужно от вас»; с листа «Roadmap» — сноски и пустые «ключевые точки»; на «ГАНТТ» — отступы
  в названиях.

**Ошибки агента.**
- Счётчики в письме, набранные руками, разошлись с картой («21 вопрос» при 22) → числа из команды `letter`.
- Предложенные ответственные попали в письмо как факт → пометка «предложение, не подтверждено».

### Этап 10. Бэкап и передача — `roadmap-10-backup`

**Как было.** «Выгрузи актуальный .zip — я хочу дальше продолжить в Codex». Архив, собранный руками, не открывался на
macOS («Ошибка 94»: нет признака UTF-8 у кириллических имён, нет пустых папок git, слишком большой). Имена файлов с «:»
и «?» не распаковывались. «Где .html файл для просмотра Roadmap? Положи его прямо в корень». Итог — `bin/backup`,
`roadmap.html` в корне, `HANDOFF.md` и `AGENTS.md` для агента без навыков. `HANDOFF.md` обновляется в конце каждой
сессии (рекомендация): продолжить может другой агент без предупреждения.

### Этап 11. Ежедневная актуализация и отчёт — `roadmap-11-daily`

**Зачем.** «Добавь для агента бриф-дейлик, чтобы он мог отвечать на вопросы в запланированной сессии, на основе данных
заполнять отчётность по Roadmap. Один запуск — один сформированный отчёт, связанный с целями Roadmap».

**Как устроено.** Запланированная сессия любого агента получает промпт `templates/daily-brief.md`: обновить репозиторий,
собрать обновления только из источников, дописать журнал и реестр по правилам этапа 8, проверить карту, собрать отчёт
`bin/roadmap daily`, коммит «Дейлик ГГГГ-ММ-ДД: …», ответ PO в 5–7 строк. Отчёт — по каждой ЦС: прогресс было → стало,
шаги, записи журнала, вопросы закрытые и новые; затем риски, следующие шаги на неделю и вопросы к PO. Пример —
`examples/school-migration/reports/daily/`.

**Ошибки агента (пробный запуск без формата).** Агент сам придумывал формат отчёта и процент цели; ЦС показывала 0%,
когда шаг был на 70%; срок ответа искался в свободном тексте → формат и правило расчёта зашиты в команду `daily`:
прогресс без своей записи — расчёт по подзадачам, срок ответа — только «до ДД.ММ.ГГГГ».

### Подготовка к созвону (по ходу любого этапа)

«Через 15 минут созвон — выведи вопросы по админкам к команде платформы Б, всё про интерфейсы. Цель — дозаполучить
ответы, какой функционал уже есть». Выборка из реестра по одной команде и одной теме с ожидаемым ответом у каждого
вопроса. После созвона ответы, сроки и статусы — в «Ответ» и «Историю».

## Приёмы, которые стоит повторять

Выведены из проекта и пробных запусков на других агентах; где это обобщение — «(рекомендация)».

| Приём | Когда | Как | Навык |
|---|---|---|---|
| **Шаг N.0 «уже работает»** (рекомендация) | часть пути объекта работает до плана | первым шагом `N.0 <объект> <что уже работает> в <системе>`: видно, откуда стартует план и что не делать заново; «Выполнено» — с доказательством | `roadmap-02-path` |
| **Технический шаг: аналитика → проектирование → доработки обеих сторон** (рекомендация) | шаг на стыке двух систем | подзадачи по порядку: аналитика (маппинг, сценарии) → проектирование (контракт обмена, согласование обеими сторонами) → доработка стороны А и стороны Б → совместная проверка; пункта нет в WBS — предложение агента и пробел | `roadmap-06-subtasks` |
| **«Подтверждено источником / мой вывод»** | объясняешь PO различия целей, схем, разбор материалов | таблица, у каждой строки — колонка «откуда»: файл и цитата или «мой вывод — подтвердить»; вывод в карту только после «да» | `roadmap-07-business-goals`, `roadmap-methodology` |
| **Ограничение — вопрос, а не допущение** | в материалах техническое ограничение («отдаёт только …», «нет обратной записи») | кандидат в реестр «как обходим / принимаем ли» с источником; в GAP и TO-BE молча не закладывается | `roadmap-03-questions`, `roadmap-05-completeness` |
| **Пишущие субагенты — в своей рабочей копии** | несколько агентов пишут файлы параллельно | у каждого git worktree или ветка; слияние по очереди, после каждого — `lint`, `check-qlinks`, коммит | `roadmap-methodology`, `roadmap-06-subtasks` |
| **Рой без Workflow — проходами** | агент без инструмента Workflow (Codex) | аудитор → скептик «источник» → скептик «покрытие» → сквозные проверки → критик, отдельными проходами с теми же заданиями и правилом вердикта | `roadmap-05-completeness`, `AGENTS.md` |
| **Комментарии к артефакту — канал правок** | PO оставил комментарии на опубликованной странице или документе | как комментарии страницы: каждый — правка в md/csv или вопрос PO, ответ — в той же ветке | `roadmap-08-comments` |
| **Сказанное в чате — по таблице «куда»** | PO пишет прогресс, ответ, срок в чат | прогресс — `journal add` + md, ответ — `question answer`, срок — «Срок ответа: до ДД.ММ.ГГГГ», реплика — `po-messages.md` | `roadmap-08-comments` |
| **`HANDOFF.md` в конце каждой сессии** | всегда | состояние, открытые решения PO, следующий шаг; следующий агент начинает с него | `roadmap-10-backup` |
| **Письмо: «в прямом влиянии PO / внешняя зависимость»** | пакет руководству | что стартует силами PO и его команд, а что ждёт внешнюю сторону — с ответственным и сроком из карты; презентация — только числа карты | `roadmap-09-leadership-pack` |

## Анти-паттерны сводно

| Анти-паттерн | Правильно |
|---|---|
| Выдуманный вопрос, ответственный, срок, эскалация | Только из источника; вывод — «предложение агента» до «да» PO |
| Декомпозиция по компонентам | Путь одного объекта по системам |
| Шаг-работа, шаг-решение, шаг-приёмка | Шаг — измеримое состояние; решение — вопрос; приёмка — DoD |
| Блокаторы вехами на Ганте | Вопросы в реестре, у задачи счётчик |
| Размазанный или составной вопрос | Точечный вопрос с ожидаемым ответом: таблица, да/нет, формула, документ |
| «Реестр полный» | Вердикт по каждому шагу, с оговорками и списком решений PO |
| Длинный реестр руководству | 3–5 измеримых решений или лист «Реестр вопросов» |
| Цифры в письме вручную | Из карты командой и сверка |
| Даты без оценки команды в пакете | Только оценка команды или выполненная работа |
| Коды WBS и ссылки на созвоны в пакете | Суть простыми словами; `Q-NN` оставить |
| Смена статуса по слову «сделано» | Кто, когда, где — потом статус |
| Свой дизайн страницы | Шаблон инструмента, правки — комментариями PO |
| Перестройка карты без показа | Проект в чате → «да» → запись |
| Вторая страница-копия стрима | Одна сборная страница цели |
| Работа без коммита и бэкапа | Коммит каждый такт, `bin/backup` по запросу и перед сменой инструмента |
| Свои скрипты для правки CSV | `bin/roadmap journal add`, `bin/roadmap question answer` |
| Срок ответа словами («к пятнице») | «Срок ответа: до ДД.ММ.ГГГГ» — его читают `lint`, дейлик и .xlsx |
| Техническое ограничение как молчаливое допущение | Вопрос-кандидат реестра с источником |
| Вывод агента звучит как факт | Колонка «подтверждено источником / мой вывод» |
| Цифры на слайде «для убедительности» | Только числа карты и команд инструмента |
